# Research Findings: `CGPreflightPostEventAccess()` process-lifetime caching on macOS

## TL;DR verdict

**Yes, the described fix is correct, and no, there is no better fully-reliable alternative.** `CGPreflightPostEventAccess()` (and its sibling `CGPreflightScreenCaptureAccess()`) read from an in-process cache that is established at (or near) launch and is **not refreshed when the user flips the toggle in System Settings while the app keeps running**. There is no public, documented, live-refreshing probe for PostEvent/ScreenCapture access. Across many independent, actively-maintained open-source macOS apps (including at least one sandboxed Mac App Store app doing the exact same PostEvent check), the consistent, convergent practitioner solution is: **detect the pending grant, then relaunch the process** with `NSWorkspace.openApplication(at:configuration:)` using `createsNewApplicationInstance = true`, followed by `NSApp.terminate(nil)` (or equivalent) once the new instance has launched. This is exactly the pattern Dictator implements, including in a **sandboxed, App-Store-style build** (`TypeWhisper/typewhisper-mac` and `arun279/t1-plus-macos`), so the pattern is both idiomatic and sandbox-compatible. Your ad-hoc-signing observation is also independently confirmed, both by Apple's own `codesign`/`csreq` tooling and by direct local reproduction: ad-hoc signing keys the code identity to the binary's **cdhash**, so each rebuild gets a new identity and invalidates prior TCC grants for that identity.

The one genuine nuance: `AXIsProcessTrusted()` is **partially** live -- several codebases show it transitioning false->true mid-session (refreshed off the undocumented `com.apple.accessibility.api` distributed notification) but **not** reliably transitioning true->false on revocation (several apps had to build a separate "live capability probe" via `CGEvent.tapCreate` for that direction). `CGPreflightPostEventAccess`/`CGPreflightScreenCaptureAccess`, by contrast, are reported by multiple independent codebases as **frozen in both directions** for the life of the process -- this is the stronger, more consistently-reported claim and is exactly what you observed with Dictator.

## Per-question findings

### 1. Is the per-process caching documented/widely reported? Is `AXIsProcessTrusted` different? Does it work when sandboxed?

- **SDK headers do NOT document any caching/relaunch behavior.** The actual doc comments for `CGPreflightPostEventAccess`/`CGRequestPostEventAccess` are a single terse line each with no mention of caching:
 `/* Checks whether the current process already has event synthesizing access */` and `/* Requests event synthesizing access if absent, potentially prompting */`
 -- `/Applications/Xcode.app/.../MacOSX.sdk/System/Library/Frameworks/CoreGraphics.framework/Versions/A/Headers/CGEvent.h:401-408` (local SDK, macOS 26 tools). Confidence: **High** (directly read).
 Similarly for Screen Recording, the header only says "If this returns false, call CGRequestScreenCaptureAccess..." with zero mention of per-process freezing -- `.../CoreGraphics.framework/Versions/A/Headers/CGWindow.h:291-300`. Confidence: **High**.
 So Apple does **not** officially document this caching behavior anywhere a developer would normally look -- it is **not an Apple-documented fact**, only an empirically/practitioner-documented one.

- **It is, however, extremely widely and consistently reported by independent practitioners reverse-engineering the exact same behavior**, strongly corroborating your empirical finding:
 - `lwouis/alt-tab-macos:src/macos/SystemPermissions.swift:226-229` (comment on `ScreenRecordingPermission.detect()`): *"`CGPreflightScreenCaptureAccess` and tccd's own checks keep answering "denied" after a mid-session grant... CGPreflightScreenCaptureAccess is frozen per-process, so it only covers the launch state."* Confidence: **High** (practitioner primary, very detailed/recent, references macOS 27 measurements).
 - `TypeWhisper/typewhisper-mac:AppStore/Sources/AppStoreInputAccess.swift:121-124`: *"The running process cannot notice the grant: CoreGraphics caches its answer, so only a relaunched TypeWhisper gets it."* This is in the **App Store (sandboxed) build** (`#if APPSTORE`), i.e. the exact deployment scenario as Dictator. Confidence: **High**.
 - `openclaw/Peekaboo:Core/PeekabooAutomationKit/Sources/PeekabooAutomationKit/Services/System/PermissionsService.swift:216-218`: *"Settings-only grants cannot be detected while this process is running because CGPreflightPostEventAccess is process-cached and no live probe API exists. Relaunch is required."* Confidence: **High**.
 - `arun279/t1-plus-macos:App/T1PlusApp/T1SupportModel.swift` (`requestEventPosting()`/`applicationDidBecomeActive()`, lines ~90-107): tracks `relaunchAfterEventPostingRequest` and relaunches once `CGRequestPostEventAccess()` returns false, confirming the same practical pattern. Confidence: **High**.
 - `mics8128/nyvox:crates/nyvox-platform-macos/src/lib.rs` (comment near lines 78-79): *"(typically still `false` until the user toggles the switch and relaunches)"* for `CGPreflightPostEventAccess`. Confidence: Medium (Rust FFI wrapper, less detailed, but independent reaffirmation).

- **`AXIsProcessTrusted()` is different, but only partially live**, per primary-source open-source evidence:
 - `lwouis/alt-tab-macos:src/macos/SystemPermissions.swift:170-175` (`AccessibilityPermission.detect()` comment): *"`AXIsProcessTrusted` answers from an in-process cache, refreshed when the distributed `com.apple.accessibility.api` arrives. System Settings posts that notification before tccd writes the change, so the refresh can capture the old value, which then sticks until the next post."* -- i.e. it DOES refresh, driven by the distributed notification, but can race and show stale values transiently. Confidence: **High**.
 - `gechr/WhichSpace:WhichSpace/Accessibility.swift:1-25` (top-of-file doc comment) and the `isRevoked`/`refreshCapability()` logic (lines ~70-78, ~210-220): *"The trust flag freezes at its launch value when permission changes in System Settings while the app runs, so revocation detection probes the live capability instead: creating an event tap is validated by WindowServer on every call."* The same file's `watchForGrant()`/`pollForGrant()` (lines 283-307) **does** successfully observe `AXIsProcessTrusted()` flipping false->true mid-session via notification + polling. So: **grant is observable live, revocation is not** (for `AXIsProcessTrusted` specifically) -- WhichSpace had to add a separate `CGEvent.tapCreate`-based live probe just for the revoke direction. Confidence: **High** (very detailed, recent, explicit practitioner documentation with reasoning).
 - `Hammerspoon/hammerspoon:Hammerspoon/MJAppDelegate.m:179,311-316` registers for the `com.apple.accessibility.api` distributed notification and re-evaluates `MJAccessibilityIsEnabled()` (wrapping `AXIsProcessTrusted`) on receipt -- a working, shipped example of live AX-grant detection without relaunch. Confidence: **High**. (Note: Hammerspoon is not sandboxed.)
 - `rxhanson/Rectangle:Rectangle/AccessibilityAuthorization/AccessibilityAuthorization.swift:36-47` simply polls `AXIsProcessTrusted()` every 0.3s with a `Timer` and it works without relaunch for the initial grant flow -- consistent with "AX trust updates live for grant." Confidence: **High**.
 - `p0deje/Maccy:Maccy/Accessibility.swift:1-9` uses a simple `AXIsProcessTrustedWithOptions(nil)` check, no relaunch logic present, consistent with the same live-grant-detection assumption. Confidence: Medium (file is small/doesn't address revocation).

- **Does `AXIsProcessTrusted` work correctly in sandboxed apps?** None of the surveyed apps that use `AXIsProcessTrusted`/`AXIsProcessTrustedWithOptions` live-updating behavior (Rectangle, Maccy, Hammerspoon, WhichSpace, AltTab) are App-Sandboxed -- they all need AX tree access/event taps that the App Sandbox forbids outright. `TypeWhisper/typewhisper-mac:AppStore/Sources/AppStoreInputAccess.swift:1-16` states explicitly: *"The App Sandbox has no access to the Accessibility API of other apps, Apple Events or event-suppressing taps. Two TCC services remain available: PostEvent... and ListenEvent..."* This is a critical finding for your case: **inside the App Sandbox, `AXIsProcessTrusted()` is essentially moot for your purposes** because you can't use the AX API on other processes anyway; `CGPreflightPostEventAccess`/`CGPreflightListenEventAccess` are the only mechanisms available to a sandboxed app, and those are the ones multiple sources confirm are frozen. Confidence: **High** (primary, in-repo documentation of the exact sandboxed scenario).

### 2. Do sandboxed apps get `kTCCServicePostEvent` vs `kTCCServiceAccessibility`, and how do they surface in System Settings?

- `TypeWhisper/typewhisper-mac:AppStore/Sources/AppStoreInputAccess.swift:9-16`: *"PostEvent (`CGEvent.post`) pastes text... System Settings lists it under Accessibility. ListenEvent (listen-only event tap)... System Settings lists it under Input Monitoring."* So the `kTCCServicePostEvent` TCC service is the one that is user-visible in the **Accessibility** pane (same pane as `kTCCServiceAccessibility`, which governs AX-tree access), while `kTCCServiceListenEvent` surfaces under **Input Monitoring**. Confidence: **High** (explicit, recent in-repo documentation, matches your empirical observation that your app shows under Accessibility).
- Independent corroboration from a security-research wiki (not Apple, but widely cross-checked, treat as Medium confidence): HackTricks' macOS TCC page explicitly lists `kTCCServicePostEvent` and `kTCCServiceAccessibility` as a pair governing related but distinct automation capabilities, both commonly escalated together -- `HackTricks-wiki/hacktricks:src/.../macos-tcc/README.md:666-668,718` ("Automation (SE) + Accessibility (`kTCCServicePostEvent`|`kTCCServiceAccessibility`) to FDA"). Confidence: Medium (reputable security wiki, not primary Apple source, but technically precise and matches TCC.db schema which is independently verifiable).
- `cua`/`seed-tcc.sh` scripts used for CI/VM provisioning list exactly `kTCCServiceAccessibility kTCCServiceScreenCapture kTCCServicePostEvent` as the three distinct services commonly pre-seeded for automation testing -- `trycua/cua:libs/images/macos/files/seed-tcc.sh:29,81`. Confidence: Medium (independent confirmation these are indeed separate TCC service identifiers, not aliases).
- Your empirical fact (a sandboxed app's `CGRequestPostEventAccess()` entry shows in the Accessibility list in System Settings) is thus consistent with these sources: `kTCCServicePostEvent` is a **separate TCC row internally**, but the **same UI list** as `kTCCServiceAccessibility`.

### 4. Is the `NSWorkspace.openApplication(createsNewApplicationInstance: true)` + `terminate(nil)` relaunch pattern common/correct for sandboxed apps? Caveats?

- **Common and correct**: it's the shipped mechanism in at least one real Mac App Store (sandboxed) app doing exactly your PostEvent scenario (`TypeWhisper`) and in a non-sandboxed-but-analogous app (T1 Plus). Both wrap it in `NSWorkspace.OpenConfiguration` with `createsNewApplicationInstance = true`, then terminate the current process from the completion handler (not before confirming the new instance actually launched) -- `arun279/t1-plus-macos:App/T1PlusApp/T1SupportModel.swift:247-263`; `TypeWhisper/typewhisper-mac:TypeWhisper/Views/GeneralSettingsView.swift:124-156`. Confidence: **High**.
- **Caveat 1 -- error handling**: both real implementations only call `terminate` inside the completion handler **after checking for `error == nil`**, so a failed relaunch doesn't leave the user with zero running instances -- this is a correctness detail worth copying if Dictator's current implementation terminates unconditionally. Confidence: High.
- **Caveat 2 -- `LSMultipleInstancesProhibited` / single-instance apps**: `TypeWhisper/typewhisper-mac:AppStore/Sources/AppStoreSingleInstance.swift:1-7` explicitly documents that *"LSMultipleInstancesProhibited would also block ApplicationRelauncher, which starts the new instance before the old one quits."* Their workaround: the old instance writes a timestamped "relaunch requested" marker to `UserDefaults` (since **launch arguments do not reach the new sandboxed instance** -- a sandbox-specific quirk) and the new instance waits for the old PID to disappear before proceeding, rather than relying on launch services to hand off cleanly. If Dictator sets `LSMultipleInstancesProhibited` (common for menu-bar/LSUIElement apps) this exact caveat applies. Confidence: **High** (explicit, detailed, sandboxed-app-specific documentation).
- **Caveat 3 -- App Sandbox itself does not forbid self-relaunch**: no source found claiming the Sandbox blocks `NSWorkspace.openApplication` for the app's own bundle; it's used successfully inside `#if APPSTORE` builds of TypeWhisper. This is consistent with Apple's own documentation of the API (`https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/createsnewapplicationinstance` -- Apple primary doc, fetched: *"the system always launches a new version of the app, even if an existing copy is already running"*), which carries no sandbox caveat. Confidence: **High** for "it works in sandbox" (demonstrated), Medium for "Apple never documents a sandbox restriction" (absence of evidence, not a guarantee).
- **Caveat 4 -- App Store review**: no direct citation found addressing review risk of self-relaunch specifically (as opposed to the broader app-relaunch pattern, which is extremely common and unremarkable -- e.g. used by update flows like Sparkle). TypeWhisper ships this exact pattern in an `#if APPSTORE` conditional, implying it has passed App Store review in that configuration, which is circumstantial but reasonably strong evidence it's acceptable. Confidence: Medium/Anecdotal (inferred from the fact that a shipping App Store build contains this code; not an explicit Apple review-guideline citation).
- Powerspaces (unsandboxed) uses a shell-script-based `kill -0`/`open` relaunch instead of `NSWorkspace`, explicitly because its app isn't sandboxed and spawns a bare process -- *"The app isn't sandboxed (it already uses private CGS APIs), so spawning it is allowed"* (`sebastianpdw/powerspaces:Sources/PowerspacesApp/AccessibilityPermission.swift:17-19,78-92`) -- implying the author believes raw process-spawning would be sandbox-restricted, which is one more data point (Anecdotal/Medium) supporting why the `NSWorkspace.openApplication` API (not raw `Process`/`posix_spawn`) is the correct sandbox-safe choice, as Dictator already does.

### 5. Ad-hoc signed apps: are TCC grants keyed to code identity / cdhash, confirmed with Apple sources?

- **Apple's own `codesign` man page, locally read**: *"If identity is the single letter "-" (dash), ad-hoc signing is performed. Ad-hoc signing does not use an identity at all, and identifies exactly one instance of code."* -- `man codesign` (local Xcode CLT installation, section SIGNING IDENTITIES). Confidence: **High** (primary Apple documentation, verbatim).
- **Apple's Code Signing Requirement Language documentation** (fetched from `developer.apple.com/library/archive/.../RequirementLang.html`) confirms the requirement language supports `cdhash H"<40-hex-digit SHA-1>"` hash constants as a first-class requirement primitive, used when there's no certificate-based identity to anchor to. Confidence: **High** (primary Apple doc).
- **Direct local reproduction** (most conclusive): built a trivial C binary, ad-hoc signed it (`codesign --sign -`), and inspected its designated requirement:
 ```
 $ codesign -d -r- t
 # designated => cdhash H"c52543b94cd9fba0f37afc305d202824d7ae589a"
 ```
 Rebuilding the **same source** and re-signing produced a **different** cdhash (`43534d433d2d5f7f832530b3442406f5cedba5e3`), confirming each build/sign cycle gets a brand-new designated requirement with no stable identity component. Confidence: **High** (reproduced locally on this machine, fully verifiable, not anecdotal).
- **Independent practitioner confirmation that TCC specifically keys off this requirement**: `sebastianpdw/powerspaces:Sources/PowerspacesApp/AccessibilityPermission.swift:7-15`: *"macOS keys the Accessibility approval to the app's code identity, so every rebuild produces a binary the old grant no longer matches. System Settings still shows the toggle on, yet `AXIsProcessTrusted()` returns false."* Their fix is `tccutil reset Accessibility <bundle-id>` + relaunch. Confidence: **High** (detailed, explicit, matches your own observed "ad-hoc rebuild breaks grants" symptom exactly).
- `gechr/WhichSpace:WhichSpace/Accessibility.swift:7-8,113-114` similarly performs `tccutil reset Accessibility <bundleID>` before prompting specifically *"to clear TCC entries keyed to a previous code signature."* Confidence: High.
- The TCC database's `csreq` column (holding the compiled code requirement blob checked at grant time) is independently documented by the HackTricks TCC wiki page, matching the schema you'd expect from the above: `select service, client, hex(csreq) from access where auth_value=2;`. Confidence: Medium (secondary/non-Apple source, but schema is directly verifiable by any developer with `sqlite3` + an admin TCC database).

### 6. Is there a better, live-updating, sandbox-compatible alternative to relaunching?

- **For `kTCCServiceAccessibility` / `AXIsProcessTrusted`-only consumers (not your case, since you're sandboxed and need PostEvent)**: yes -- listening for the `com.apple.accessibility.api` distributed notification (Hammerspoon) or combining it with polling plus a settle delay (WhichSpace, AltTab) does observe a **grant** live, no relaunch needed. AltTab instead prefers the private/undocumented Darwin notification `com.apple.tcc.access.changed` for better ordering guarantees (`lwouis/alt-tab-macos:src/macos/SystemPermissions.swift:5-10`). Confidence: High that this works for AX trust specifically.
- **For revocation** of AX trust mid-session, no app found a way to get `AXIsProcessTrusted()` itself to flip back to false live; WhichSpace had to build an independent live capability probe using `CGEvent.tapCreate`/`tapIsEnabled` as ground truth (`gechr/WhichSpace:WhichSpace/Accessibility.swift:203-220`). Confidence: High (detailed, reasoned practitioner source) -- but note `CGEvent.tapCreate` against other processes is itself an Accessibility-gated, non-sandboxed capability, so this workaround is **not available to a sandboxed app** either.
- **For `CGPreflightPostEventAccess`/`CGPreflightListenEventAccess` specifically (your actual situation), no live/sandbox-compatible alternative was found in any surveyed source.** Every app that needs this exact permission (TypeWhisper App Store build, T1 Plus, Peekaboo, nyvox) converges on: poll/cache a "we asked but aren't granted yet" flag, detect the user's return to the foreground (`applicationDidBecomeActive`/`didBecomeActiveNotification`), and then **relaunch**. None of them found or built a live probe for PostEvent access -- multiple of them state explicitly that none exists (`openclaw/Peekaboo:.../PermissionsService.swift:216-218`: *"no live probe API exists"*; `TypeWhisper/typewhisper-mac:AppStore/Sources/AppStoreInputAccess.swift:122`: *"The running process cannot notice the grant"*). Confidence: **High** -- this is a consistent negative result across every independent codebase surveyed, which is about as strong as open-source evidence gets for "this doesn't exist."
- Conclusion: **relaunch genuinely is the most reliable current workaround for `CGPreflightPostEventAccess` in a sandboxed app**, and Dictator's implementation matches the community-converged best practice closely (the main improvement to consider is the error-handling/"only terminate after confirming the new instance launched" detail from TypeWhisper/T1 Plus, and the `LSMultipleInstancesProhibited` handoff caveat if that entitlement/plist key is set).
